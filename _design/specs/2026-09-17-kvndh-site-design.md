# kvndh.com 사이트 설계

- 작성: 2026-09-17 (HQ 세션)
- 상태: 사용자 승인 (구조, 만드는 방식, 작업 순서)
- 저장소: `KVNDH/KVNDH.github.io` (공개), 작업 브랜치 `site-v1`

## 1. 목적

출시된 iOS 앱 5개의 **소개, 지원(FAQ와 문의), 개인정보 처리방침**을 `kvndh.com` 한곳에 모은다.
보는 사람은 세 부류다.

- 앱스토어 방문자: ASC 의 마케팅 URL, 지원 URL, 개인정보 처리방침 URL 로 들어온다
- SNS와 광고 유입: 앱별 페이지에서 설치로 이어져야 한다
- 앱 목록을 한눈에 보려는 사람: 허브 페이지

이 사이트가 앞으로 **마케팅 문구와 개인정보 처리방침의 기준**이 된다. 각 앱의 스토어 문안과 ASC URL 은 앱 업데이트 때 이 사이트에 맞춘다.

### 2-1. 이미 끝난 인프라 (2026-09-17)

- cafe24 DNS
  - `kvndh.com` A → `185.199.108.153`. cafe24 는 루트 A 레코드를 **하나만** 허용한다. GitHub IP 는 CDN 이라 하나로 동작한다
  - `www` CNAME → `kvndh.github.io`
  - `*.kvndh.com` CNAME → `kvndh.com`. cafe24 가 자동으로 만든 것이며, 사용자 결정으로 유지한다
  - `_github-pages-challenge-KVNDH` TXT: GitHub 도메인 인증용이다
- GitHub Pages: 사용자 도메인 `kvndh.com`, HTTPS 강제, 도메인 인증 `verified`. 인증서 자동 갱신(첫 만료 2026-12-16)
- `kvndh.github.io/*` 와 `kvndh.github.io/support/*` 는 `https://kvndh.com/...` 으로 넘어간다
- `app-ads.txt` 는 `https://kvndh.com/app-ads.txt` 에서 열린다(AdMob). **어떤 배포에서도 이 파일이 루트에 있어야 한다**

## 3. 문구 규칙

사이트 전체, 8개 언어에 적용한다. 스토어 문안은 "메타데이터 통일" 작업 때 같은 규칙으로 맞춘다(범위 밖, 7절).

1. **앱만 담백하게 소개한다.** 만든 사람 이야기를 쓰지 않는다.
   금지 예: "iOS 앱을 혼자 만듭니다", "1인 개발", "직접 만든", "~을 위한 앱을 만듭니다"
2. **"개인정보가 기기 밖으로 나가지 않습니다" 계열 표현을 쓰지 않는다.** 한국 정서에 맞지 않는다.
   금지 예: "기기 밖으로 나가지 않음", "어디에도 올라가지 않음", "서버로 전송되지 않음", "사진은 기기 안에 있습니다"
   - 소개 문구에서는 편의와 사실로 말한다: "회원가입 없이 바로 사용", "작업 내용은 앱에 저장"
   - 개인정보 처리방침에서는 5절의 표준 목차로 사실만 담담하게 적는다
3. **말투(ko)**
   - 문단은 짧은 합니다체
   - 불릿은 명사형으로 끝낸다. 예: "표식 없는 저장", "10초~90초 타임랩스", "한 번 구매, 구독 없음"
   - 해요체와 2인칭(당신, 여러분)은 쓰지 않는다
4. **기호**: 문장 안의 가운뎃점 `·`, 전각대시(U+2014), 전각 괄호 `【】` 를 쓰지 않는다. `어플` 이 아니라 `앱`
5. **AI 말투 금지**: "혁신적인", "놀라운 경험", "~의 모든 것", "지금 바로 시작하세요!" 같은 빈 수식어
6. **사실은 코드에서 확인한다.** 가격, 무료 한도, Pro 혜택, 구매 방식(1회 구매, 구독 여부), 광고 SDK, 권한은 앱 저장소 코드와 `.storekit`, `PrivacyInfo.xcprivacy` 에서 읽는다. 스토어 문안을 그대로 믿지 않는다
7. **기능 이름과 버튼 이름**은 그 언어의 앱 화면 표기(번역 카탈로그)와 같게 쓴다. 앱이 그 언어를 지원하지 않으면 영어 표기를 쓴다
8. 다른 언어는 ko 와 en 의 **구조**(섹션 순서, 항목 수)를 따르고, 말투는 그 언어의 관례를 따른다
9. **Pro 는 고급 기능으로 소개한다.** "Pro에서는 이런 것까지 된다"를 보여 주고, 구매 방식은 강조하지 않는다(사용자 지시 2026-09-17)
   - 소개 문구 금지: "한 번 구매", "구독 없음", "일회성 구매", "고급 기능은 Pro"
   - 가격 안내, 무료와 Pro 비교표도 두지 않는다
   - 구매 복원 같은 실무 안내는 지원 페이지 FAQ 에만 둔다

### 3-1. 문장 계약 (사용자 지시 2026-09-17: beautiful-prose 기준, AI 말투 제거)

모든 언어의 문구는 사람이 쓴 것처럼 자연스러워야 한다. 아래를 어기면 실패로 본다.

**쓰는 법**
- 무엇을 하는 앱인지부터 말한다. 분위기 잡는 첫 문장이나 후킹 문구로 시작하지 않는다
- 추상어보다 **구체 명사**를 쓴다: 물감, 붓자국, 격자선, 잠금화면, 주사위 눈
- **동사를 앞세운다.** "~할 수 있습니다"를 늘어놓지 않고 "바꿉니다", "쌓입니다"처럼 바로 말한다
- 문장 길이를 섞는다. 비슷한 길이의 문장을 다섯 개 연달아 쓰지 않는다. 짧은 문장은 힘을 줄 곳에만 쓴다
- 앞 문장을 다시 말하는 문장, 요약으로 끝맺는 문장, 감정을 유도하는 문장은 지운다
- 세 개짜리 나열은 실제로 셋일 때만 쓴다. 균형을 맞추려고 문장이나 항목을 채우지 않는다
- 느낌표를 쓰지 않는다. 확신이 서지 않으면 **덜 쓴다**

**금지 (ko)**
- 수식어: 혁신적인, 놀라운, 완벽한, 특별한, 스마트한, 강력한, 직관적인, 손쉽게, 간편하게, 쉽고 빠르게, 차원이 다른, 새로운 차원, 한 단계 업그레이드, 똑똑하게
- 반전 구문: "단순한 X가 아닙니다", "X가 아니라 Y입니다", "X뿐만 아니라 Y까지"
- 권유와 광고투: "지금 바로", "이제 ~하세요", "~을 경험하세요", "~을 만나 보세요", "더 이상 ~할 필요 없습니다"
- 감성 상투어: 여정, 소중한 추억, 특별한 순간, 나만의 특별한, ~의 모든 것

**금지 (en)**
- em dash, "not just X, but Y", "It's not X, it's Y", "whether you're X or Y"
- seamless, effortless, elevate, unlock, unleash, dive into, journey, cherished, game-changer, stunning, powerful, intuitive
- "take X to the next level", "at your fingertips", "like never before", "say goodbye to", "all-in-one"

**다른 언어**: 같은 원칙을 그 언어의 흔한 AI 표현에 적용한다. 예시는 다음과 같다.
- ja: 「革新的」「シームレス」「〜の全て」「新たな体験」
- zh: 「无缝」「全新体验」「开启…之旅」
- de: „nahtlos" „mühelos" „auf ein neues Level"
- es: „sin esfuerzo" „al siguiente nivel"
- pt-br: „sem esforço" „para o próximo nível"

## 5. 개인정보 처리방침 구조

개인정보보호위원회 작성지침의 목차 순서를 따른다(모든 언어 같은 순서). 수집이 없으면 "없음"을 분명히 적는다.

1. 개인정보의 처리 목적
2. 처리하는 개인정보의 항목
3. 처리 및 보유 기간
4. 제3자 제공
5. 처리 위탁
6. 파기 절차와 방법
7. 정보주체와 법정대리인의 권리와 의무, 행사 방법
8. 안전성 확보 조치
9. 자동 수집 장치의 설치와 운영, 거부 방법. 광고 식별자와 쿠키. 해당이 없으면 "없음"
10. 개인정보 보호책임자와 문의처(`kvndh36@naver.com`)
11. 권익침해 구제 방법(개인정보분쟁조정위원회, 개인정보침해신고센터 등 공공 기관 연락처)
12. 처리방침의 변경과 시행일

- **앱별 사실 출처**: `PrivacyInfo.xcprivacy`, 링크된 SDK(Package.resolved, Podfile, package.json), Info.plist 권한 문구, `.storekit`, ASC 앱 개인정보 라벨. 인앱 결제는 Apple 이 처리한다는 점을 적는다
- **Tapey 는 Google AdMob 을 쓴다.** 광고 식별자(IDFA)와 추적 허용(ATT), Google 로의 제공 또는 위탁을 사실대로 적는다. 법적 표현은 **사용자 검토 필수**
- 목업에 들어간 확인 안 된 문장("만 14세 미만", "사진 권한은 고를 때만" 등)은 코드로 확인되기 전에는 쓰지 않는다
- 시행일은 배포일로 한다

## 6. 만드는 방식

### 6-1. 폴더

```
content/
  site.json                  언어 목록, 앱 순서, 문의처, 강조색
  i18n/<lang>.json           공통 UI 문자열 (메뉴, 버튼, 꼬리, 언어 이름)
  apps/<app>/facts.json      코드에서 뽑은 사실 + 출처 파일 경로
  apps/<app>/<lang>.json     소개, FAQ, 개인정보 처리방침 문구
templates/                   base, hub, app, support, privacy, root, 404 (Python string.Template)
assets/<app>/                icon (180, 360 WebP), shots/<lang>/NN.webp, og.jpg
static/                      app-ads.txt, CNAME, robots.txt, .nojekyll (docs/ 로 그대로 복사)
scripts/build.py             content + templates → docs/ (표준 라이브러리만)
scripts/check.py             검사기 (아래)
docs/                        생성 결과. GitHub Pages 공개 폴더
_design/                     목업, 스펙, 자산 키트 (공개 안 됨)
```

- **CSS**: 공통 CSS 하나를 빌드 때 페이지마다 인라인으로 넣는다. 외부 CDN, 웹폰트, 원격 이미지는 쓰지 않는다
- **스크립트**: `/` 의 언어 이동 하나만 쓴다. 나머지 페이지는 스크립트 없이 동작한다
- **이미지**: 스크린샷은 각 앱 저장소의 스토어 스크린샷에서 가져와 WebP 로 줄인다. 그 언어의 스크린샷이 없으면 en 을 쓴다
- **`build.py` 는 결정적**이어야 한다. 같은 입력이면 같은 출력이 나온다. 빌드 날짜는 넣지 않는다

### 6-2. 검사기 (`check.py`)

실패가 하나라도 있으면 배포하지 않는다.

- **문구**
  - 3절의 금지 표현(개발자 자기소개, "기기 밖" 계열, AI 수식어, `어플`)
  - `·`, U+2014, `【】`
  - ko 의 해요체와 2인칭
  - ko 불릿이 명사형으로 끝나는지
- **구조**: 8개 언어의 섹션 수와 FAQ 수, 개인정보 처리방침 12개 절이 ko 와 같은지
- **사실**
  - `<lang>.json` 의 숫자와 구매 방식이 `facts.json` 과 맞는지
  - Tapey 개인정보 처리방침에 AdMob 항목이 있는지
- **링크**: 내부 링크와 앵커가 전부 있는지, App Store 링크의 앱 ID 가 맞는지, `hreflang` 짝이 맞는지
- **파일**: `docs/app-ads.txt`, `docs/CNAME`(내용 `kvndh.com`), `docs/404.html`, `docs/.nojekyll` 이 있는지. 최상위 `docs/support/` 가 없는지

## 7. 작업 순서 (멀티에이전트)

작업은 `site-v1` 브랜치에서 한다. 서비스 중인 `main` 은 배포 때까지 건드리지 않는다. 에이전트는 모두 10개다.

| 단계 | 담당 | 내용 | 끝나는 조건 |
|---|---|---|---|
| 0. 뼈대 | HQ | 폴더, 템플릿(C안), `build.py`, `check.py`, `site.json`, `i18n/ko.json`. 한국어 허브와 BrushWorks 페이지 3종을 샘플로 만든다 | 사용자가 샘플을 보고 승인 |
| 1. 앱별 사실과 문구 | 에이전트 5개 (앱당 1개) | `facts.json`(출처 경로 포함), ko 와 en 문구(소개, FAQ, 개인정보 처리방침), 스크린샷과 아이콘 자산. **앱 저장소는 읽기만 한다** | `check.py` 의 ko와 en 부분 통과 |
| 2. 번역 | 에이전트 3개 | ja / zh-hans와 zh-hant / de와 es와 pt-br. 앱 번역 카탈로그 용어를 따르고, 개인정보 처리방침은 같은 12절 구조 | `check.py` 구조 검사 통과 |
| 3. 검토 | 에이전트 2개 | ① 문구 규칙, 사실, 법적 표현을 코드와 대조 ② 전 페이지를 390px, 1200px 로 렌더링해 화면, 접근성, 링크 확인 | 지적 목록 |
| 4. 수정 | HQ | 지적 반영, `check.py` 전부 통과. Tapey 개인정보 처리방침은 사용자 검토 | 사용자 확인 |
| 5. 배포 | HQ, **사용자 확인 뒤** | 아래 6단계 | 전 주소 확인 |

### 7-1. 배포 절차

1. `docs/` 에 `CNAME`, `app-ads.txt`, `.nojekyll`, `404.html` 이 있는지 `check.py` 로 확인한다
2. `site-v1` 을 `main` 에 합쳐 푸시한다
3. Pages 공개 폴더를 `main /` 에서 `main /docs` 로 바꾼다(`gh api -X PUT repos/KVNDH/KVNDH.github.io/pages`, cname 과 https 유지)
4. 빌드가 끝나면 확인한다
   - 새 주소 전부(8개 언어 × (허브 + 앱 5개 × 3종) + `/` + 404)
   - `https://kvndh.com/app-ads.txt`
   - 옛 `https://kvndh.com/support/*.html` 과 `https://kvndh.github.io/support/*.html`
   - `http`, `www` 가 `https://kvndh.com` 으로 넘어가는지
5. 문제가 있으면 공개 폴더를 `/` 로 되돌린다. 루트의 옛 `index.html` 과 `app-ads.txt` 는 배포 뒤 한 주기 동안 지우지 않는다
6. HQ 가 결과를 보고한다

## 8. 범위 밖 (앱 업데이트 1~3번 작업 때)

- 앱마다 새 버전을 낼 때 ASC 의 마케팅, 지원, 개인정보 처리방침 URL 을 4-2 대응표대로 바꾼다(각 앱 세션)
- 모든 앱이 바뀐 뒤 `KVNDH/support` 페이지를 새 주소 안내 페이지로 바꾼다
- asc-upload 규칙(`~/.claude/skills/asc-upload/`)과 검사기를 새 말투("불릿은 명사형")와 3절 규칙에 맞게 고친다. **전역 스킬이라 사용자 확인 뒤에 한다**
  - 알려진 검사기 빈틈: 해요체를 홍보문구에서 잡지 않음, 불릿 기호 누락을 놓침
- 스토어 문안의 Pro 설명에서 "한 번 구매하며 구독이 아닙니다" 류 강조를 뺀다
  - asc-upload 규칙 4-1 은 "1회 구매 여부를 적는다"고 되어 있어 3절 9번과 충돌한다
  - 규칙을 고칠 때 함께 정리한다
- 스토어 문안의 "기기 안" 계열 표현 정리(BrushWorks "■ 사진은 기기 안에 있습니다", Tapey 홍보문구 등)
- Life Tyde Android 판은 다루지 않는다

## 9. 위험과 대응

| 위험 | 대응 |
|---|---|
| 공개 폴더를 바꿀 때 `app-ads.txt` 가 빠져 AdMob 인증이 끊김 | `check.py` 필수 검사 + 배포 직후 확인 |
| 개인정보 처리방침의 사실 오류 | `facts.json` 출처 경로 + 검토 에이전트 대조 + Tapey 는 사용자 검토 |
| 기계 번역 말투 | 언어별 관례 지시, 검토 에이전트, 원어민 검수는 없음을 기록 |
| 앱 세션과 파일 충돌 | 에이전트는 앱 저장소를 읽기만 한다 |
| 옛 지원 링크 끊김 | `KVNDH/support` 는 이번 작업에서 건드리지 않는다 |
